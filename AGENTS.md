# Emmy

Emmy is a flexible chief-of-staff operating kit for one ChatGPT Dot and delegated Work or Codex tasks. Default coding to local Codex. Treat cloud Work, the Dot's cloud computer, Codex Cloud, and each connected Mac as separate environments.

## Start each session

1. Read `README.md`, `docs/architecture.md`, and `.agents/skills/verify/features/README.md` when present.
2. Run `npm run agent -- doctor`, then `npm run agent -- maintain --check` when those commands exist.
3. Apply installed `pstack:poteto-mode` for work across files, architecture choices, and unknown bugs. Apply the standing thread and model policy below throughout all Emmy work.
4. Read the relevant project verification skill before changing behavior. Keep its feature map, command metadata, and docs in sync with code.

## Finish each change

Run `npm run check`. Run the behavioral driver and bounded formal verifier after changes to their covered code. Review the code-to-property mapping and replay failing mutations. Refresh generated docs. Never advance a formal sync record without reviewing the covered diff.

Run the installed pstack maintenance workflows when features or covered code change. The local maintenance command detects drift and regenerates derived content. It does not replace independent source reading, live driving, or reviewing formal assumptions.

## Standing thread and model policy

Create a fresh project-bound thread for each distinct new objective. Continue an existing thread only when continuing that same objective and its context is needed. A shared repository or topic is insufficient. Rediscover uncertain dispatches before retrying so an ambiguous launch cannot create duplicate work.

When private project bindings select an authorized persistent native dispatcher, recover it and the objective through the trusted installed `dispatch` command before routing. Keep that dispatcher pinned for coordination. It creates fresh coding children; implementation belongs to those children. Use [private dispatch recovery](docs/native-dispatch.md), existing source authorization and parent-owned native progress. The command is read-only advice, not a native hook or access grant. Exact dispatcher and job identities remain private.

Before creating a native child for a user objective, follow [structured native task preparation](docs/native-dispatch.md#prepare-a-native-task-from-saved-project-guidance). Validate the original task record and pass the resulting prompt unchanged to the native tool. This is agent-mediated invocation with deterministic input validation.

Use the designated host's native `mcp__codex_app__create_thread` with the discovered saved project ID and `target.environment.type = "local"`. `cloud_threads.create` durable tasks do not prove native creation. When Emmy lacks native tools directly, use the existing authorized control bridge for native creation and parent-owned `read_thread` or `wait_threads` progress. Do not depend on the coding chat waking Emmy. Resolve pending client IDs through native discovery before using ready thread operations. See [the concrete route](docs/change-delivery.md#create-through-the-native-host-service).

Discover the saved native project before dispatch. After creation, read back the returned thread's actual saved project membership and compare its project ID with the intended saved project. A working directory, request parameter, or returned thread ID alone does not prove membership. Retain the native thread ID, project ID, executor/host readback, requested settings, and verification time privately. If membership is missing, attach that same thread through the supported native project operation and read it back. If membership is unavailable or ambiguous, retain it as unverified and rediscover before any retry. Do not create a replacement thread to repair an uncertain association or edit native databases. Preserve contrary owner observations alongside later readbacks. See [the dispatch contract](docs/change-delivery.md#verify-the-created-threads-project-membership).

Name model policy by family and effort. Resolve that choice against the destination host's current supported model catalog immediately before dispatch. Concrete API calls and saved schedules need a supported model ID; a prose alias does not make the runtime resolve it. Preserve the family and effort, record the resolved version and catalog evidence privately, and fail clearly if unavailable or ambiguous. Never silently substitute another family or effort. Existing threads keep their selections. Saved automations keep their concrete ID until a supported update is authorized and verified.

Choose for the actual task, including expected retries, verification, and handoff cost. Do not try an underpowered model first merely because its nominal price is lower. These are starting policies, not measured rankings between model families:

| Task group | Default | Change the choice when |
| --- | --- | --- |
| Ordinary coding lead; substantial diagnosis or review | Sol Medium | Use Sol High for heavy reasoning; no higher without exact-task one-time owner permission. |
| Daily improvement coordinator | Sol Medium | Substantive helpers use Sol Medium; use Sol High only for heavy reasoning. |
| Bounded implementation with understood cause and acceptance; nontrivial helper | Sol Medium | Use Sol High only for heavy reasoning. |
| Mechanical helper with known target and supplied inputs | Luna Max | Use Sol Medium or High before starting if the task needs investigation or judgment. |
| Computer Use and UI diagnosis | Terra High | Use Medium for an established bounded routine; XHigh for an evidenced difficult UI/reasoning problem. |
| Read-only routine evidence collection or suggestions | Sol Medium | Use Luna Max only for a clearly specified extraction; High for ambiguous conflicting evidence. |
| Established deterministic automation | Luna Max | Use a capable Sol or Terra lead when new interpretation, debugging, or meaningful repair is required. |
| Exceptional architecture or difficult root-cause analysis | Sol High | Above High or another coding model requires exact-task one-time owner permission. |

Ordinary coding sessions and substantive helpers use Sol Medium. Heavy reasoning uses Sol High maximum. Anything above High or another coding model requires explicit ONE-TIME owner permission for the exact task, role, model and effort. No Astra default or automatic XHigh escalation. Generic "or higher" is insufficient. This scoped coding/helper policy overrides pstack role defaults; other established task groups and unrelated automation selections remain unchanged. Luna uses Max only for established groups outside this coding/helper scope. Terra UI settings remain separate. Effort names compare settings within one model.

Standard/non-fast is the default for coding sessions, coordinators and helpers. Fast or Ultrafast requires explicit owner approval for that exact task, role and tier. An unanswered request is not approval; continue Standard without waiting. Never inherit an accelerated tier from a parent, saved session or broader preference. Model/effort permission does not grant speed permission. Use supported native/config controls only, verify recorded settings separately, and report an unavailable tier control or readback.

A trivial subagent performs one bounded action with a known target and supplied inputs. Investigation, architecture, unknown bugs, and cross-file implementation are nontrivial. Luna is not a mandatory first attempt. Escalate unexpected failures or scope growth with their evidence instead of repeating weak attempts. The lead independently reviews a helper's actual diff and verification.

Honor explicit human model and effort instructions within their named scope. Project `.codex/config.toml` supplies concrete startup defaults; it is not a dynamic family resolver. The dispatch coordinator translates this family policy into exact supported requests and scoped overrides accepted by the existing dispatch contract. Do not edit global settings or another project's defaults. Distinguish requested policy, resolved ID, recorded settings, and observed execution. If any readback is unavailable, report it.

All agents and subagents apply the installed pstack principles, not only the lead. Resolve and read the actual skill, pass its path plus the relevant project verification and authority requirements in every delegation, and retain one owner per change. These scoped model rules override conflicting pstack role defaults. Use the [official-source allocation rationale](docs/research/model-allocation.md) and local measurements to refine choices; never invent a model mapping or task benchmark.

## Daily improvement

Follow [the daily review procedure](docs/daily-improvement.md). Review prior-day evidence and unreviewed gaps, preserve verified repairs, make justified bounded reversible fixes, and report substantial changes with impact and rollback. Reuse existing responsibilities and the existing daily briefing. Keep suggestions separate from implementation. A derived report, a local patch, and a manual rescue do not prove deployment, adoption, or a repaired recurring trigger.

## Persistent calendar planning

Follow the calendar procedure in [the delivered operating brief](docs/operating-brief.md#plan-and-maintain-calendar-tasks). Find existing Tasks, choose slots, and create, move, or resize the same saved items within the user's concrete scope. Preserve Task versus Event intent and native IDs. Use capable connectors first and the supported Calendar UI in the current verified execution environment when duration needs it. Follow the operating brief's environment and identity checks. A connected Mac's browser is a separate environment. Reopen saved items to verify their fields. Keep intent and readbacks in existing private notes or responsibilities. No recurring schedule is needed to establish this procedure.

## Evidence and scope

Label facts as documented, observed, reported, inferred, or unverified. A generated packet is a proposal. It is not a dispatched task, installed Dot configuration, saved schedule, merged PR, deployed site, or verified outcome.

Keep private machine paths, conversation IDs, raw app transcripts, account snapshots, tokens, and personal task state under ignored `.local/`. Commit only public project metadata and sanitized evidence. Never store credentials.

Prefer one owner per coding change and isolated worktrees for concurrent writers. Keep the human-facing plan concise. Give Emmy useful responsibilities and room for judgment. Add a new restriction only for a demonstrated boundary or explicit human requirement.
