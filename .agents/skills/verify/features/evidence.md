# Reconciliation and correction

## User route

Run `reconcile --id <id> --import <bundle> --as-of <UTC>`, or omit `--id` to review all responsibilities. Imports are optional. Actual local inspection supplies current git identity and artifact bytes. Review output includes context, effective cutoff, observation refusals, criterion support/assurance, open findings, exact repairs, corrections/regressions, and proposals.

Every live review includes actual completion time, including cloud, unbound, or conflicting targets that produce no local observations. The requested `asOf` remains in `requestedAsOf`; fixed historical replay uses its pinned time. Imported future, stale, partial, unavailable, or foreign records remain diagnostics. New eligible coverage does not erase a retained failure. Rechecks must follow the latest failure, name the exact finding/original failure, bind the current expected subject, and satisfy every original affected criterion. Weaker criteria cannot close old failures. Two repeated actual failed repairs propose diagnosis even after native completion. That continuation requires fresh native rediscovery; pending/uncertain effects keep rediscovery-only priority, and expired scope yields observation/decision. Exact closure suppresses duplicate completed green work.

A local-check pins a repository-relative Node script, digest, arguments, expected exit, finite timeout, and separate `run-local-check` authority. Its source/output/exit/runtime are retained. Reported imports cannot acquire local assurance. Required independent review remains externally blocked.

Before each executable criterion, the canonical inspector reacquires repository path, repository identity, revision and dirty bytes. A mismatch or unreadable identity yields unknown evidence without executing that command. Restored eligibility uses the pinned epoch and observations with a fresh live cutoff for each command. Earlier source-changing failure remains retained. Post-execution inspection still detects changes during execution. These checks do not atomically pin filesystem bytes or revoke running commands.

Each child records at most one cleanup attempt across output, timeout, cancellation, exit, and close callbacks. Successful signalling waits for close, including normal leader exit with inherited descendants. An owned process-group signal denied with `EPERM` produces failed evidence with `process-group-cleanup-failed`, its process-group ID, and `cleanup.status = unverified`. The operation stops waiting without claiming termination. Cancellation reports the same uncertainty as an operational error. An unverified group may still contain processes; the driver records its later fixture cleanup separately. The original observed EPERM cause remains unresolved.

## Boundaries

An earlier passing repair stays in its immutable review when later deterioration makes that attempt currently insufficient. A native run, useful outcome, and delivered notification require separate evidence. Only a known explicit due window is evaluated; later windows need native discovery. Retired methods stop their local-check execution, preserve failures, and expose pending native disablement. Imported enabled/disabled contradictions need explicit scope-safe supersession.

Briefing consistency is advisory. Its reviewed source manifest does not prove new formal policy. Downloaded guidance executes no code and grants no authority. Output receipts never replace correction storage. Native invocation, later-turn recovery and exact displayed output remain unverified until their actual probes pass.

The approved two-document briefing bundle includes standing thread/model rules, the concrete native project creation route, bridge-owned progress readback, and the persistent calendar procedure. `maintain --write` regenerates that data. The real briefing drive verifies transport, exact delivered bytes, and the returned calendar section's notes contract. It requires requested notes and source URLs, exact text and meaningful line breaks, Save followed by reload and same-ID reopen, saved-contents comparison, pending acceptance for missing or mismatched notes, and inspection before a supported visible retry. Three weakened bundles pass transport and return through the real CLI, but the driver rejects generic popup presence, generic labels as proof, and nonempty text without the exact saved-field comparison. These controls cover delivered instructions only. They do not execute Calendar, compare native notes, or enforce the procedure. After publication and installation, perform a real canonical guidance refresh and inspect the returned text and digest. Native thread creation requires separate create, saved-membership and reopen receipts. Session settings, provider execution, cross-device visibility, and later-turn adoption remain separate observations. Native Calendar creation, duration, notes persistence, and duplicate prevention require the dedicated native acceptance contract.

Native calendar acceptance separately covers Task/Event identity, all requested saved fields, notes persistence, duration, move, inventory coverage and timezone consistency. A notes repair reuses the existing authorized Task and supplied text without requiring another Task or marker. Compare the actual saved Task notes field for the same native ID with the requested contents and source URLs. Generic popup text, Description labels, nonempty boilerplate, and rendered drafts cannot pass. Missing, blank, truncated, mismatched, or unreadable saved notes remain pending. A partial save cannot pass overall completion. Retries require actual input through supported controls, blur and Save, reload, and a same-ID saved readback. Retain raw intended and actual notes and any trailing-space delta. Do not trim or normalize values to claim exact identity. Content preserved with an explicit delta remains distinct from exact-match acceptance. A resize cannot prove a move. Free/busy can omit Tasks and transparent Events. Conflicting Calendar/embedded-Task clocks stay unresolved until attributable time/zone evidence or an explicit decision resolves them, separately from notes acceptance. The delivered procedure requires those distinctions; the fixture driver does not prove native enforcement. Later unrelated human-turn acceptance requires its own guidance, fresh-thread membership and actual model readbacks, without a setup reminder.
