# Bounded history exporter

The experimental batch-v2 exporter preserves one registered owner, one anchor and the original full source scope. Existing batch-v1 APIs and remote inventory-v2 and anchor-v1 schemas remain available. Production adoption is blocked pending accounting review, exact-shape capacity evidence, independent review and native runtime acceptance.

`src/automation-reporting-bounded.mjs` exposes `beginBoundedHistory`, `advanceBoundedHistory`, `advanceBoundedPublication`, `respondBoundedPublication`, `recoverBoundedPublication` and `retryBoundedPublicationRead`. The [behavioral mapping](../verification/automation-reporting/bounded-coverage.md) describes the executable controls and remaining gaps.

Each request names an ordinary absolute `stateDirectory`, a stable admitted `jobId`, and a distinct callback `executionId`. A continuation supplies the exact returned `jobLedger`. Capture continuation also supplies the returned `captureId` and `cursor`. A changed request does not renew a claimed execution. A separate execution marker prevents reuse of an execution ID under a newer ledger cursor. The exclusive claim reserves remaining allowance before source work. An unfinished claim leaves allowance unavailable and leaves any provider effect uncertain.

The [accounting revision](../verification/automation-reporting/bounded-accounting.md) defines native evidence categories. A ticket has a hard maximum of262144 representation bytes,32 reserved provider-call permissions,10000 filesystem read and write operations and120000 milliseconds. A live ticket accepts at most128 callbacks. The file entrypoint starts its absolute deadline before controller inspection. An absolute `attemptDeadline` can tighten the original120000-millisecond deadline. Continuations cannot renew it. Actual provider cancellation is not established. Each local window advances at most64 durable transitions. These cooperative bounds do not admit a fleet ticket or enforce provider-wide limits. The parent owns native admission and actual connector calls.

Accounting separates acquired and generated representations, actual filesystem bytes and operations, reserved provider permissions and known returned provider attempts. Prior provider counters stay explicitly unknown until the exact predecessor ledger is validated. An unresolved accounting ledger cannot grant later permissions. A pending reservation is unavailable allowance, not measured usage. Every actual source or private-state reread is acquired again. Persisting an already charged exact raw buffer once adds write traffic without another evidence representation. Accounting revision `native-evidence-v2-identical-utf8-once` treats canonical text and its identical UTF8 buffer as one logical representation. Internal metadata, decode buffers and transient diagnostic serialization have separate process counters. They do not add fleet evidence bytes. Base64 and new retained JSON frames remain distinct representations.

A live runtime reuses only already charged immutable buffers from the same ticket and exact prior ledger. A new ticket or process acquires those bytes again. Mutable body, raw and explicit recovery paths bypass caches, including paths with64-hex ancestors. Cache reuse is limited to immutable internal state under the private root. Each actual read checks the open descriptor and ordinary path again after the bytes, using full identity and unchanged ancestry; same-size drift or replacement leaves receipt acceptance held. The runtime does not cache the source tree or mutable assembly files. Reports retain original source clocks and explicit nulls. Production capture derives its start before the first source observation and its end after the final membership and metadata fence. The retained header keeps the original start across restarts. Production requests omit both capture clock fields or supply null. Supplying either clock requires `synthetic: true`. Synthetic fixtures can provide a fixed ordered interval.

Capture proceeds through census, first pass with immediate predecessor checks, deferred predecessor pairs, optional preceding-history comparison, second pass and final membership and metadata checks. Immutable indexed descriptors and exact raw shards survive process restarts. The final job checks every source identity and modification clock again before sealing. These observations establish temporal consistency under immutable producer-file assumptions. They do not establish an atomic filesystem snapshot or future latest state.

Publication stores one intent before each effect. Tool actions use a local `file_uri`. Raw download responses retain the original response object and a separate exact raw file. Per-object response cells replace whole-journal replay. Inventories assemble canonical fragments into a bounded durable file. Upload and pointer mutations are never blindly reissued. A missing read response requires an explicit known-ID refresh, which creates a new action and permission. Recovery binds an acquired exact upload ID and still requires metadata and raw readback.

Successors compare complete admitted history and audit predecessor generations incrementally. Grant and poison compete for the same next immutable owner-turn slot under the existing anchor namespace. Each turn binds the exact previous turn digest, owner, anchor and scope. A grant binds an already durable intent and ancestor-audit cursor. The exclusive hard link is the commit point. A losing grant retains its intent and returns no new permission. It cannot skip the winning turn or reissue after a crash. Poison is terminal, so no later grant can commit.

Response acquisition first commits a `receipt-open` owner turn, competing with a grant for the same exclusive next slot. It binds validated original capture, cursor, action, generation, owner/scope, admission claim hashes, job/execution and unchanged acquisition deadline. One receipt can be open. No new grant or other receipt can commit until that exact attempt resolves or becomes terminal poison. The file entrypoint validates bounded launch origin IDs using charged private state before opening, then acquires the body. Canonical in-memory API input is snapshotted before awaits; the caller retains responsibility for its earlier acquisition and retains input until acceptance. The exporter does not claim control of that earlier boundary.

An open attempt establishes uncertainty, not full receipt retention. Exact acquired input is copied to an owned immutable artifact, with size/hash and original identity binding. Actual separate raw bytes have their own pre-read identity record and owned copy. An evidence notice can precede those copies; its planned outcome is not acceptance or closure. Missing, changed or corrupt bytes remain a held gap. An accepted exact buffer is charged once; persistence still adds actual writes and operations. Response acquisition reserves an additional8192 evidence bytes and256 filesystem operations for retention before accepting bytes. These reservations are separate from known actual counters and the terminal summary allowance.

`recoverReceipt: {open, inputPath?, rawPath?}` explicitly reconciles one exact old attempt under a fresh, separately admitted ticket. `open` is the original sequence/digest receipt. Optional caller-retained paths must satisfy the original full file identity or previously retained exact hash and origin; a path or size alone is insufficient. Missing original raw-source binding cannot be reconstructed from a changed caller path. No absent-byte, hash-only, age, PID or administrative closure restores eligibility. Recovery retains the old deadline as historical and uses its own unchanged deadline. A `receipt-resolved` turn requires the owned actual input, exact original binding and matching retained response. Every receipt turn preserves the last-grant lineage, so intervening receipts cannot erase action or generation order.

A contradiction commits terminal poison before any derived canonical conflicting-response variant or poison mirror. Full owned raw input can precede poison and remains evidence even if no additional wrapped variant fits. A crash during acquisition or retention leaves the pre-acquisition open turn discoverable and held. An expired acquisition cannot copy payload, accept or resolve a receipt, or commit a grant or poison. After terminal poison, unique immutable evidence-only intake markers bind that poison and the later validated origin before acquisition. They can retain second and third actual variants without appending an owner turn, reopening eligibility or claiming that missing variants were fully retained.

The original winning callback can return its exact `permissionCommit` receipt. The receipt is explicitly historical, and `currentEligibility` remains `not-established`. A delayed return cannot authenticate a fresh permission or cancel an already dispatched RPC. Observing later or unverified owner activity withholds `execute`. A losing or restarted callback never redelivers the grant. Parent admission and actual effect remain separate.

Full-journal audit reads retain256 filesystem operations for the existing cursor commit. The reservation reduces ordinary allowance. Only complete validated cells advance the audit index. It is released only around that bounded transition; `budgetStopped: true` then ends the64-window callback, so ordinary reads cannot spend its unused margin. A caller must retain the exact returned cursor/ledger and obtain separate admission before continuing. The synthetic driver uses a distinct ticket identity, retains all previous actual ledgers and forwards exact checkpoint custody for body-unread progress. An accepted unresolved receipt requires explicit recovery rather than response replay.

Every commit operation still checks the unchanged operation cap and original deadline. The256-operation margin covers the tested ordinary and EEXIST cursor paths; partial I/O, unusually deep ancestry or commit failure can exhaust it and leave a truthful gap. It does not permit borrowing operations or claiming an uncommitted index. Older capacity forecasts remain scoped historical results; new synthetic ticket totals do not establish retained peak capacity, archive support or operational readiness.

Owner-head navigation starts from the verified turn retained in a capture cursor. Each forward edge validates exact bytes, owner/scope, sequence, previous digest, retained grant/receipt evidence and last-grant generation/action order. One pass traverses at most32 edges. `ownerHeadCheckpoint` names an exact immutable verified checkpoint for explicit continuation. Its returned-only `receipt` binds `jobId`, `executionId` and the exact `jobLedger`; the durable ledger contains the simple checkpoint reference, avoiding a self-hash cycle. A fresh admitted ticket charges and validates that ledger, its exclusive primary/execution claims, original timing/predecessor, capture/origin cursor, and owner/root/scope/admission binding. A bare caller hash is a target hint without skip authority. Current-call progress has explicit verified per-Job custody. Each starting head also validates its evidence, immediate predecessor and last-grant continuity. If navigation uses the remaining intake allowance, its verified progress returns before the body is read. Response origin stays separate from navigation progress. These are normal charged inputs, never free control metadata. Unknown, missing, corrupt or conflicting state fails closed. No mutable latest pointer is trusted. The new `bounded-history-v2-custody-ledger-1` capture revision refuses earlier experimental captures rather than silently migrating their missing grant history. Historical failed read responses remain attached to their original actions when an explicit refresh succeeds. Pointer closure requires the exact desired raw readback.

The single-command CLI accepts `begin`, `advance`, `next`, `respond`, `recover` and `retry-read` with `--file ABSOLUTE_REQUEST --launch JSON`. The generated standalone command uses `history-bounded ACTION` with the same options. The `live` command accepts JSON lines containing `action`, an absolute request `file`, and `launch`. Each line is bounded to4096 bytes. Its enclosing JSON frame is charged once; nested launch fields are not added again. The process returns one JSON result per line and performs no provider calls.

Launch JSON is limited to2048 bytes. It contains only `stateDirectory`, `jobId`, `executionId`, the registered controller's decimal `controllerDev` and `controllerIno`, optional exact `jobLedger` and `attemptDeadline`, and bounded `captureId`, `cursor`, `actionId`, a recovery-open selector and bounded `ownerHeadCheckpoint` custody receipt when required. Response origin IDs are mandatory and are normal charged state inputs, not free controller authority. The controller identity comes from the already registered ordinary state directory. File-first bootstrap fails closed. A charged `beginBoundedHistory` call with in-memory input first validates ordinary source and state ancestry, disjoint paths, owner and scope. It then retains `bounded-controller.json` in the existing state ledger. That bounded profile binds the source root, state directory identity, owner and scope digest. The marker grants no native admission or provider permission. Checkpoint custody is excluded from the free status-controller input and checked under normal ticket accounting before receipt-open. The charged registered profile is also loaded before receipt-open. A prior ledger contains only its returned `cursor`, `size`, `chargedBytes`, `startedAt` and `deadline`. The request path is limited to1024 bytes. These fields cannot contain source headers, scope, shards or batches.

The file entrypoint checks this metadata, the registered profile and the execution marker before acquiring any request body. Unregistered or overlapping state refuses without body acquisition or writes. Normal execution reacquires and charges the exact profile and binds each body or capture header to it before source observations. Normal ticket accounting reserves the predecessor claim and validates the prior ledger before `Job.read` acquires the body. Every acquired byte is charged, including malformed or changed inputs. Error reasons are limited to256 characters, with `reasonTruncated` explicit, so an oversized filesystem message cannot displace the durable accounting ledger. The body must match the admitted state, job, execution, prior ledger and deadline. Missing, oversized or expired inputs grant no action. A refused or unfinished claim keeps the original reservation unavailable. Automatic retry stops. When insufficient allowance prevents admission, a bounded controller writes an execution refusal without reading the body. Controller diagnostics remain separately attributed. Neither status nor refusal grants source or provider permission.

A distinct terminal finalization window lasts at most2000 milliseconds and uses the already reserved8192 bytes for one ledger-write attempt and returned status. After the original acquisition deadline it emits only refusal, incomplete or uncertain status from known memory counters. Every durable job ledger is evidence-only: `status: incomplete`, `execute: false`, `ledgerRole: historical-accounting-only` and historical core status/grant receipt. The separately charged returned JSON carries the actual current outcome. Only the original winning callback can return timely execution permission. A completed earlier result returned late is historical with `execute: false`. A deadline crossing during actual ledger I/O therefore cannot leave a positive durable permission. No source/private payload reread, provider call, raw copy, acceptance/closure, owner turn, claim rearm or automatic retry is permitted. A conflicting or failed terminal ledger exposes uncertainty for separate admission. Claim creation failures also retain known acquired/generated counters and any uncertain claim write; they do not reread or rearm a claim. Actual complete writes, uncertain partial writes, generated summary representation and returned output remain separately accounted. This bounded result interval does not extend acquisition time. Custody assumes cooperating immutable private cursors, claims and ledgers plus actual returned receipts; hashes do not authenticate an entirely forged private state.

The status-only controller accepts `status` with exact launch and registered controller identity flags. It reads at most4096 bytes of claim metadata and grants no source execution. Its input and output are each separately bounded, with an8192-byte combined limit. Novel controller authorization still requires independent review.
