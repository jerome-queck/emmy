# Bounded history exporter

The experimental batch-v2 exporter preserves one registered owner, one anchor and the original full source scope. Existing batch-v1 APIs and remote inventory-v2 and anchor-v1 schemas remain available. Production adoption is blocked pending accounting review, exact-shape capacity evidence, independent review and native runtime acceptance.

`src/automation-reporting-bounded.mjs` exposes `beginBoundedHistory`, `advanceBoundedHistory`, `advanceBoundedPublication`, `respondBoundedPublication`, `recoverBoundedPublication` and `retryBoundedPublicationRead`. The [behavioral mapping](../verification/automation-reporting/bounded-coverage.md) describes the executable controls and remaining gaps.

Each request names an ordinary absolute `stateDirectory`, a stable admitted `jobId`, and a distinct callback `executionId`. A continuation supplies the exact returned `jobLedger`. Capture continuation also supplies the returned `captureId` and `cursor`. A changed request does not renew a claimed execution. A separate execution marker prevents reuse of an execution ID under a newer ledger cursor. The exclusive claim reserves remaining allowance before source work. An unfinished claim leaves allowance unavailable and leaves any provider effect uncertain.

The [accounting revision](../verification/automation-reporting/bounded-accounting.md) defines native evidence categories. A ticket has a hard maximum of262144 representation bytes,32 reserved provider-call permissions,10000 filesystem read and write operations and120000 milliseconds. A live ticket accepts at most128 callbacks. The file entrypoint starts its absolute deadline before controller inspection. An absolute `attemptDeadline` can tighten the original120000-millisecond deadline. Continuations cannot renew it. Actual provider cancellation is not established. Each local window advances at most64 durable transitions. These cooperative bounds do not admit a fleet ticket or enforce provider-wide limits. The parent owns native admission and actual connector calls.

Accounting separates acquired and generated representations, actual filesystem bytes and operations, reserved provider permissions and known returned provider attempts. Prior provider counters stay explicitly unknown until the exact predecessor ledger is validated. An unresolved accounting ledger cannot grant later permissions. A pending reservation is unavailable allowance, not measured usage. Every actual source or private-state reread is acquired again. Persisting an already charged exact raw buffer once adds write traffic without another evidence representation. Accounting revision `native-evidence-v2-identical-utf8-once` treats canonical text and its identical UTF8 buffer as one logical representation. Internal metadata, decode buffers and transient diagnostic serialization have separate process counters. They do not add fleet evidence bytes. Base64 and new retained JSON frames remain distinct representations.

A live runtime reuses only already charged immutable buffers from the same ticket and exact prior ledger. A new ticket or process acquires those bytes again. The runtime does not cache the source tree or mutable assembly files. Reports retain original source clocks and explicit nulls. Production capture derives its start before the first source observation and its end after the final membership and metadata fence. The retained header keeps the original start across restarts. Production requests omit both capture clock fields or supply null. Supplying either clock requires `synthetic: true`. Synthetic fixtures can provide a fixed ordered interval.

Capture proceeds through census, first pass with immediate predecessor checks, deferred predecessor pairs, optional preceding-history comparison, second pass and final membership and metadata checks. Immutable indexed descriptors and exact raw shards survive process restarts. The final job checks every source identity and modification clock again before sealing. These observations establish temporal consistency under immutable producer-file assumptions. They do not establish an atomic filesystem snapshot or future latest state.

Publication stores one intent before each effect. Tool actions use a local `file_uri`. Raw download responses retain the original response object and a separate exact raw file. Per-object response cells replace whole-journal replay. Inventories assemble canonical fragments into a bounded durable file. Upload and pointer mutations are never blindly reissued. A missing read response requires an explicit known-ID refresh, which creates a new action and permission. Recovery binds an acquired exact upload ID and still requires metadata and raw readback.

Successors compare complete admitted history and audit predecessor generations incrementally. Grant and poison compete for the same next immutable owner-turn slot under the existing anchor namespace. Each turn binds the exact previous turn digest, owner, anchor and scope. A grant binds an already durable intent and ancestor-audit cursor. The exclusive hard link is the commit point. A losing grant retains its intent and returns no new permission. It cannot skip the winning turn or reissue after a crash. Poison is terminal, so no later grant can commit.

Contrary raw bytes and their full original response first enter an explicitly pending invalidation frame. Every later publication request checks pending or unknown invalidation evidence before obtaining another grant. A poison CAS losing to an earlier prepared grant reconciles that winner boundedly. Pending evidence blocks future grants until poison commits. Canonical contrary variants follow the poison turn and shared/local poison mirrors. Crashes and losing CAS attempts preserve actual evidence. They do not clear poison, discard a variant or renew allowance.

The original winning callback can return its exact `permissionCommit` receipt. The receipt is explicitly historical, and `currentEligibility` remains `not-established`. A delayed return cannot authenticate a fresh permission or cancel an already dispatched RPC. Observing later or unverified owner activity withholds `execute`. A losing or restarted callback never redelivers the grant. Parent admission and actual effect remain separate.

Owner-head navigation starts from the verified turn retained in a capture cursor. Each forward edge validates exact bytes, owner/scope, sequence, previous digest and generation order. One pass traverses at most32 edges. `ownerHeadCheckpoint` names an exact immutable verified checkpoint for explicit continuation; it is ordinary charged private-state input, never free control metadata. Unknown, missing, corrupt or conflicting state fails closed. No mutable latest pointer is trusted. The new `bounded-history-v2-owner-turn-1` capture revision refuses earlier experimental captures rather than silently migrating their missing grant history. Historical failed read responses remain attached to their original actions when an explicit refresh succeeds. Pointer closure requires the exact desired raw readback.

The single-command CLI accepts `begin`, `advance`, `next`, `respond`, `recover` and `retry-read` with `--file ABSOLUTE_REQUEST --launch JSON`. The generated standalone command uses `history-bounded ACTION` with the same options. The `live` command accepts JSON lines containing `action`, an absolute request `file`, and `launch`. Each line is bounded to4096 bytes. Its enclosing JSON frame is charged once; nested launch fields are not added again. The process returns one JSON result per line and performs no provider calls.

Launch JSON is limited to2048 bytes. It contains only `stateDirectory`, `jobId`, `executionId`, the registered controller's decimal `controllerDev` and `controllerIno`, and optional exact `jobLedger` and `attemptDeadline`. The controller identity comes from the already registered ordinary state directory. File-first bootstrap fails closed. A charged `beginBoundedHistory` call with in-memory input first validates ordinary source and state ancestry, disjoint paths, owner and scope. It then retains `bounded-controller.json` in the existing state ledger. That bounded profile binds the source root, state directory identity, owner and scope digest. The marker grants no native admission or provider permission. A prior ledger contains only its returned `cursor`, `size`, `chargedBytes`, `startedAt` and `deadline`. The request path is limited to1024 bytes. These fields cannot contain source headers, scope, shards or batches.

The file entrypoint checks this metadata, the registered profile and the execution marker before acquiring any request body. Unregistered or overlapping state refuses without body acquisition or writes. Normal execution reacquires and charges the exact profile and binds each body or capture header to it before source observations. Normal ticket accounting reserves the predecessor claim and validates the prior ledger before `Job.read` acquires the body. Every acquired byte is charged, including malformed or changed inputs. Error reasons are limited to256 characters, with `reasonTruncated` explicit, so an oversized filesystem message cannot displace the durable accounting ledger. The body must match the admitted state, job, execution, prior ledger and deadline. Missing, oversized or expired inputs grant no action. A refused or unfinished claim keeps the original reservation unavailable. Automatic retry stops. When insufficient allowance prevents admission, a bounded controller writes an execution refusal without reading the body. Controller diagnostics remain separately attributed. Neither status nor refusal grants source or provider permission.

Its input and output are each separately bounded, with an8192-byte combined limit. Novel controller authorization still requires independent review.
