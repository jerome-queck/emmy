# Private automation reporting

The reporting CLI reads validated immutable outcomes. Existing improvement-report producers and fleet responsibilities still own reporting and monitoring. This hub never reruns gameplay, quizzes, mail, Tasks or calendar actions. No remote service, OAuth, installation or account permission is needed for local operation.

```sh
mkdir -m 700 /absolute/private/reporting-store
npm run reporting -- --help
npm run reporting -- status --directory /absolute/private/reporting-store
npm run reporting -- import-improvement --directory /absolute/private/reporting-store --namespace maintenance --automation-id daily-maintenance --file /absolute/private/compact-report.json --dry-run
npm run reporting -- import-improvement --directory /absolute/private/reporting-store --namespace maintenance --automation-id daily-maintenance --file /absolute/private/compact-report.json
npm run reporting -- list --directory /absolute/private/reporting-store --limit 50 --query unresolved
npm run reporting -- serve --directory /absolute/private/reporting-store
```

Use an existing absolute canonical directory without symlink ancestry. `serve` prints its loopback URL and binds only `127.0.0.1`; stop its owned process with Ctrl-C. GET-only HTTP serves the same validated model. There are no rerun or cancellation controls.

## CLI contract

Each invocation prints one JSON result. Exit 0 means its local operation completed, 2 means invalid input or an operational refusal, and 3 means findings requiring attention. A completed review with partial evidence is a valid execution outcome; `coverage-partial` is evidence attention, not execution failure. Missing reports and delivery remain separate. Empty inventory means registered-only coverage with unknown undiscovered automations, never complete fleet coverage.

`status`, `diagnose` and `reconcile` return concise counters and bounded findings (20 by default), with `findingPage` totals and `--finding-cursor` continuation. `inspect` returns typed detail pages (50 per kind by default), totals and digest continuation cursors without a duplicate records array. Namespace/automation scope filters apply to all reads. These commands read the bounded store without writes or native actions. `validate` and `dry-run` validate a supplied record and ownership without writes. `publish-own-record` requires `--namespace` matching the envelope. `export-outcome --id <current-run-digest> --to <absolute-private-output>` writes a bounded sanitized outcome file without cloud calls. It refuses incomplete scans, invalid/conflicted/superseded runs, known credentials, private paths/account addresses in exported text, and unsafe artifact URLs. Identical output retries converge; different existing bytes remain unchanged. `get --id` retrieves an exact immutable digest, including historical revisions. `list` supports namespace, automation, bounded search, digest cursor and limit 1–200. Its cursor addresses observed immutable IDs; restart pagination to discover concurrent insertions before a cursor. CLI help lists exact flags. The existing `agent reporting --file <request.json>` exposes the same core JSON operations.

Scans inspect at most 200 root entries and 5,000 namespace entries, including pending files. Each record is bounded to 32 KiB. Exceeding a bound or finding corrupt/mismatched canonical bytes yields explicit incomplete coverage and suppresses accepted run execution. Pending write bytes are ignored within those bounds. A scan may precede a later write and is not a transactional filesystem snapshot. No all-account completeness claim follows.

## Version 1 record schema

Every envelope has exactly `schemaVersion`, `namespace`, `automationId`, `kind`, `key`, `revision`, `previous`, `recordedAt`, and `data`. Version is 1. Namespace and automation ID are safe identifiers of at most 120 characters. Keys retain bounded original logical identities, including compact-report run IDs; keys never form filesystem paths. Timestamps are canonical UTC. Revision zero has null predecessor. Later revisions reference the exact prior digest, same identity, preceding revision and nondecreasing record clock. Run occurrence identity and receipt subject stay fixed. Missing or invalid predecessors and divergent leaves remain visible and unusable.

`automation` data contains `name`, `enabled`, `schedule`, `environment`, `nativeRef`, `model`, `destination`, nullable `freshChat` and `archiveOnSuccess`, `sourceRef`, and `observedAt`. It preserves declared native configuration; it does not configure a scheduler. Freshness checks the original native observation, not just the latest envelope.

`occurrence` data contains `scheduledFor` and `expiresAt`. Expected slots exist independently of observed invocations. An expired slot without a validated run is overdue. Invalid or conflicted invocation evidence leaves the slot unknown. No slot or archive membership implies completion.

`run` data contains nullable `occurrenceKey`, `execution`, `coverage`, nullable `report`, and bounded `evidenceRefs`. Execution is unknown, running, blocked, pending-approval, completed, failed or skipped. Terminal execution cannot change state in a successor. A retry uses a new invocation key. Same-state successors can append corrected report/coverage evidence; old facts remain immutable. Coverage is complete, partial or unavailable. Optional `telemetry` contains measured `runtimeMs`, `inputTokens`, `outputTokens` (unavailable values are null), and `sourceRef`. Optional `timing` contains nullable `startedAt`, `lastHeartbeatAt`, `endedAt`, plus `observedAt` and `sourceRef`. Event times are ordered and no later than the source observation; observation is no later than the envelope. Omitted timing projects explicit nulls. Report generation, import and envelope clocks never become actual run events. Values are supplied measurements, never estimates of provider billing. The reader preserves raw measured values; it invents no trends from missing telemetry.

The report union also accepts generic `type: automation-outcome`, `schemaVersion: 1` for briefing, URECA, Krillion, Wooclap and future workflows. Exact fields are `schemaVersion`, `type`, `runId`, `provenance`, nullable manual `scheduledFor`, `status`, `coverage`, `availability` (available/unavailable), `summary` (at most 600 characters), `artifactLinks` (bounded safe HTTPS label/URL pairs), nullable original `sourceWindow`, and `generatedAt`. Available requires a compact outcome or artifact. Generic availability is preserved independently of execution. No review kind is invented for unrelated workflows.

The compact report is the existing [improvement-report validator](../src/improvement-report.mjs) v1 contract. Its execution/coverage/run identity must match the envelope, and scheduled provenance must match the exact occurrence time. `import-improvement` uses deterministic slot identity and scheduled-time bytes for the occurrence, preserving the original report generation time on the run. Distinct attempts for one slot therefore share one expected occurrence. Manual reports create no expected slot. Publication retry is safe after interruption between the two immutable writes and never replays the underlying work.

`publication` and `delivery` data contain exact run digest `subject`, `state` (pending, accepted, verified or failed), and nullable `evidenceRef`. Verified requires an evidence reference and cannot regress in a successor. Subjects must be current valid nonconflicting runs in the same producer scope and precede the receipt. Acceptance is not verified publication; publication is not user delivery. Both remain attributable reported claims. Their references do not authenticate a provider or recipient.

`issue` data contains bounded searchable `title`, state open/acknowledged/resolved, and `evidenceRefs`. Resolution requires evidence. Immutable revisions retain acknowledgements and later reopenings. Only compact sanitized outcomes and safe artifact references belong in these records. Keep secrets, raw logs, full mail and sensitive account payloads out. Publication rejects recognized API-key, Bearer, private-key and credential-URL patterns. Cloud export explicitly selects compact outcome fields and hashed timing references; it excludes local evidence refs. Its additional policy refuses recognizable local paths, account email addresses, raw headers and credential-bearing URLs. Refusal leaves publication pending. These bounded lexical checks cannot establish that arbitrary prose contains no secret; producers still own sanitization.

## Storage and ownership

Each producer writes only `<store>/<namespace>/<sha256>.json`. The SHA-256 covers recursively sorted JSON. A fully written fresh pending file is hard-linked to the canonical digest, read back, then the owned pending file is removed. Identical retries converge; differing records are retained. Readers derive the view from all validated facts; producers never write a shared index or dashboard. Namespace selection is cooperative ownership, not OS-user authentication. Ordinary trusted private directories, collision-resistant hashes, atomic same-filesystem hard links and no hostile concurrent ancestor replacement are assumptions. No power-loss durability follows.

`pendingPublicationQueue` derives from runs without a verified publication receipt. Retrying that queue means retrying reporting only. Private sync/publication and the existing ChatGPT notification workflow remain parent-owned. No new notification channel is created. Keep a pending notice distinct from an independently verified user delivery.

Inventory native and cloud definitions before migrating adapters, including disabled definitions and missing fields. Preserve authority, timings, model, destination and lifecycle fields privately. Parent owns cloud prompt changes. Future prompts publish their own bounded outcome after work and preserve original workload success criteria. Expected slots come from the existing fleet/schedule owner, independently of whether a producer invokes. Reporting retries never replay effects. Missing or uncertain sync remains pending and must use the existing failure-notification workflow.

The source repository is public. Keep runtime records, raw logs, native IDs and personal state under ignored `.local/` or the verified private operational folder. Never push them to public source. Git metadata/push permissions do not prove private runtime access. No new private GitHub repository, visibility change, credentials or permissions are implied.

Exactly one dedicated native local upkeep automation maintains managed names, paths, safe links and freshness in the verified private reporting copy. It does not invent outcomes, edit artifact content or permanently delete anything. It requires verified local deployment and synced mapping. Preserve other schedules/models. Identical retries converge after interruption. Original plans retain names so aliases can be recreated for a deliberate rollback. File/namespace case aliases are retained; actual APFS tests cover sole-entry deletion and duplicate spellings. Unknown and pending files, stale/missing outcomes and unproven links remain findings. One cooperating writer and immutable source/candidate bytes are assumptions. Local moves/coalescing do not preserve or establish Drive file IDs or sync atomicity.

Synced namespaces must already exist and have verified mapping. Missing folders remain pending; transport and upkeep never provision them locally. The generic publisher's `--synced` guard requires an exact existing namespace and export-safe record. The installed primary-store launcher applies it automatically; ignored fallback publication can still initialize its own namespace. Provision future folders through exact Drive parent IDs, verify remote metadata and actual local arrival, then enable the writer. A local mkdir is not Drive identity proof.

It computes bytes/hash without changing supplied values. Actual code enforces cross-field clocks/privacy; schema documents structure. Namespace ancestry needs a separate complete namespace read. An unavailable cloud Node runtime is a blocker; install nothing, use the existing authorized native bridge. Native source artifact readability does not prove execution in another environment.

Provider invocation IDs are used only when actually exposed by trusted context. Otherwise persist a generated opaque producer-invocation ID before upload, explicitly label its source, and keep provider ID unavailable. Never present it as a native/provider ID or replay work to recover it. The existing fleet/schedule owner independently publishes expected occurrences under its delegated authority; expected slots do not prove a trigger. If a native invocation starts before its expected slot, `execution: running` with `report: null` and actual sourced timing is valid. Scheduled generic reports cannot predate their slot; retain missing report rather than advancing clocks or changing the legacy review contract. Existing workload authority/time guards remain separate.

Empty inventory and enabled definitions with no observed invocation require attention and explicit unknown/observation-needed state, without inventing failed runs. Disabled definitions require no new run. Reported completion and partial coverage remain independent. Per-automation detail links its latest recorded evidence IDs; that selection is not proof of the latest native invocation.

## Independent expected occurrences

The existing report upkeep actor also performs registration control. It writes schemaVersion2 `registration` and `expectation` envelopes only in its configured control namespace. Every registration names the target producer namespace/automation, exact saved native identity, enabled status, RRULE/actual DTSTART, explicit timezone and its provenance, scheduling fingerprint, original source observation/digest, observation grace and maximum source age. Producers keep schemaVersion1 records in their own namespaces. A caller supplies the expected control identity; a record's actor string never grants registration authority. The read-only join does not grant cross-producer writes.

```sh
npm run reporting -- expectations --directory <private-fallback> --namespace <control-owner> --file <private-control-config>

```

Planning is read-only by default. Its clock and source digest remain original. A local reread never becomes fresh cloud native evidence. Source capture must independently precede the producer; imported historical occurrences remain correlation evidence only.

The finite projection supports configured DAILY/WEEKLY UTC or Asia/Singapore rules, actual DTSTART for COUNT/INTERVAL, and bounded lookahead. Unsupported rules, missing anchors/zones and unavailable captures stay pending. Null next_run_time never becomes a future occurrence. This projection starts no job and never changes a saved recurrence or workload authority. Stable target/fingerprint/UTC slot keys reuse exact records on retries. Fresh actual observations append registration successors; edits or disabled definitions withdraw future expectations after the observed change boundary. Actual earlier edit timing remains uncertain and old immutable bytes remain retained.

Selected configurable policy is eight planning days, 3,600 seconds observation grace and 172,800 seconds source freshness. These are reporting parameters. Grace says when an observation gap needs attention; it is not an execution deadline, timeout or proof of failure. Source age bounds configuration evidence, not execution authority. An expected slot without a run retains execution `not-inferred`; after grace it becomes `observation-gap`. Running can remain running after grace. Only explicit producer evidence reports failed execution. Incomplete/conflicted/missing control dependencies and stale sources keep applicability unknown.

The existing upkeep call acquires native definitions, reads the configured cloud input, reconciles its own control records, projects its own namespace through transport, and publishes bounded per-target binding snapshots to preprovisioned exact-ID private System configuration files. One cooperating control writer and exact post-update readback are required. Drive update has no compare-and-swap guarantee. The frozen cloud tool's `bind` action validates exact configured target/control identity, all supplied dependency lineage, registration fingerprint, source freshness, snapshot expiry and the exact nominal scheduled slot. Use the scheduler-supplied trusted `Run` context as nominal evidence where actually exposed, normalized to UTC. It is not actual start time. Missing nominal evidence returns `scheduled-unbound`; never select the wall-clock nearest slot or label scheduled work manual. A fresh persisted opaque invocation key and retained exact predecessor receipts permit routine own-run preparation without listing all historical records or depending on a per-run native bridge. The actual cloud capability/read route is a deployment prerequisite. A supported one-time capture or successful create/update response does not establish automatic discovery of later manual cloud edits. ## Readable scheduled-unbound outcomes

A scheduled invocation without trusted current nominal metadata can publish a readable `automation-outcome` schemaVersion2. Its provenance is `scheduled-unbound`, `scheduledFor` and the run's `occurrenceKey` are null. Never infer a slot from current time, the schedule rule, native turn start or Last run. Never relabel it manual. Existing generic outcome v1 remains unchanged for manual and exactly bound scheduled reports.

Outcome v2 retains the existing summary, availability, execution, coverage, artifact links, original sourceWindow and generatedAt. It adds `sourceEvidence: {observedAt, recordedAt}`, each an original supplied UTC clock or null, and `generation: {mode, attestedBy, basedOn}`. Mode `producer` requires basedOn null. Mode `retrospective` names the exact prior immutable run digest. AttestedBy is a bounded reported compiler label, never an authority grant. GeneratedAt is actual report creation, not a new provider observation. A retained record clock does not become gameplay timing. Unknown original clocks and window remain null.

A retrospective first attachment uses the same invocation's successor, exact previous digest and revision+1, preserves terminal execution, coverage, timing and telemetry, and requires the prior report to be null. SourceEvidence.recordedAt equals that predecessor's original record time; known original observation and window end cannot follow it. An identical attached report can survive later evidence-only revisions, but content/mode replacement is refused. Inspect the complete current own history and native inactive state before a retrospective write; if the head advanced or conflicted, stop. The immutable publisher can retain concurrent branches as a visible conflict, not a false clean winner. Keep every original null-report revision.

Transport preserves v2 content and original clocks, remaps its retrospective basis through the exact source-to-target digest map, and retains unchanged legacy target bytes. Sanitized outcome export is version2 only for this new content. Summary availability, execution, unknown nominal identity, original evidence age and report generation stay distinct in CLI and dashboard. An unbound readable outcome never satisfies an independent expectation; its execution remains reported and expectation execution stays not-inferred. Original evidence age cannot be refreshed by new report/wrapper clocks. No supplied original clock means unknown source age, not freshness.

Reporting interchange schema v3 adds this new nested version while retaining strict unchanged v1/v2 schemas. Run envelopes remain version1 and registration control remains version2. New readers accept legacy records. Old readers, schemas and frozen tools refuse nested outcome v2 and can mark mixed scans incomplete. Install the compatible reader before adoption; keep it when rolling back production of new content. Do not delete records or point a legacy reader at the live mixed store to hide incompatibility.

`npm run build:reporting-cloud` emits the new `automation-reporting-cloud-v2.mjs`, all three schema files and a version2 source manifest. ## Immutable admitted-history publication and discovery

`npm run reporting:history -- --help` exposes a durable private publication operation. This supplements local transport and upkeep. It does not install an autonomous local connector. The existing authorized publication actor executes supported Drive calls. No workload, schedule, recipient, credential or collector authority follows.

Before bootstrap, admit the producer's complete retained TARGET namespace history, including old revisions, conflicting branches, failed attempts, null reports and actual TARGET publication/delivery receipts. Supply the stable admission ID and explicit `completeAdmittedHistory: true`. This declares a producer boundary. It cannot prove hidden writers or arbitrary provider-folder completeness. The exporter reads exact canonical bytes twice, rejects pending/corrupt entries and changed captures, validates ancestry, and preserves original clocks. It never exports the sanitizer's receipt-skipping projection or upkeep's repair map.

One registered publication owner controls one exact anchor ID. Owner namespaces are disjoint. Put the private journal, immutable inventories and anchors outside canonical Records directories. The approved scope v2 contains the v1 record scope with a pages placeholder and registered owners. Each owner supplies `owner`, `anchor: {id,parentId,name}`, `inventoryParentId`, `namespaces` and `singleWriter: true`. Shared anchors and multiwriter deployments are refused. A local per-anchor immutable claim chain serializes competing batches in the same private state directory. Independent state directories and hostile external writers remain unsupported. Drive has no claimed compare-and-swap or globally atomic latest pointer.

Bootstrap is concrete. The parent first creates a new raw JSON anchor outside Records, retains the returned exact ID, and verifies metadata and complete raw bytes. Its canonical body has `schemaVersion: 1`, `kind: "automation-reporting-discovery-anchor"`, the approved `owner`, `generation: 0`, and `inventory: null`. Bind that exact ID/parent/name into scope before preparing the first batch. Discovery reports publication-pending until generation one closes. A different owner, arbitrary bootstrap body or preexisting unrelated anchor refuses advancement. Anchor creation is separately scoped parent work.

Prepare accepts a private JSON request containing `directory`, an existing `stateDirectory` outside Records, approved `scope`, `owner`, integer `generation`, `admission: {id,completeAdmittedHistory:true}`, `captureStartedAt` and optional `captureEndedAt`. Generation one has `previous: null`. Later requests carry `previous: {reference,inventory}` with the exact preceding immutable inventory bytes and reference. Every prior source descriptor must survive. Admission identity remains stable and capture intervals cannot overlap. The bounded format admits at most 200 root entries, 5,000 total records, 16 MiB source bytes, 32 MiB packets and 5,000 lineage generations. Individual source and inventory bytes retain the capture consumer's existing bounds.

```sh
npm run reporting:history -- prepare --file /absolute/private/prepare.json
npm run reporting:history -- next --file /absolute/private/batch-request.json
npm run reporting:history -- respond --file /absolute/private/actual-response.json
npm run reporting:history -- recover --file /absolute/private/exact-id-recovery.json
npm run reporting:history -- retry-read --file /absolute/private/readback-refresh.json
npm run reporting:history -- materialize --file /absolute/private/upload-intent.json
```

The batch request contains `stateDirectory` and returned `batchId`. `next` publishes an immutable intent before returning a connector action. Only `status: "action-required"` with `execute: true` permits that action. `respond` adds `actionId` and the actual normalized response. A pending upload on restart returns uncertain and forbids another create. `recover` additionally supplies the exact returned `id` and retained `evidence`; recovery establishes an ID only, followed by actual metadata and complete raw readback. Name search never recovers an ID. Crashes before the provider call and after an unknown upload can be indistinguishable. Without retained exact-ID evidence, uncertainty remains visible. A failed known-ID metadata/raw response can be refreshed explicitly with `retry-read`, supplying `stateDirectory`, `batchId`, the current failed `actionId` and bounded `evidence`. Each of at most twenty retries per exact object readback appends an event and new metadata/raw attempt IDs, preserving every previous raw response. Both metadata and complete raw bytes are reacquired, including after a raw-download failure. Upload intents cannot use this operation. Duplicate retry requests are idempotent.

The async `publishHistory(request, adapter)` source API calls the adapter itself and retains every actual response before semantic validation. It is more than a supplied-receipt validator. Supported methods are `uploadImmutable({name,parentId,bytesBase64})`, `getMetadata({id})`, `downloadRaw({id})` and `updatePointer({id,name,parentId,bytesBase64})`. The actor maps these respectively to existing `upload_file`, `get_file_metadata`, `fetch` and `update_file` operations. Before any upload/update effect, `next` materializes an immutable private payload file, rereads it, and returns `artifact: {path,size,sha256}` plus exact supported tool operation/arguments. `materializePublicationUpload` and CLI `materialize` verify the same artifact again from its retained action ID. Async adapter upload/update arguments include this optional artifact. The actor uses that file only when supported by its actual runtime, or materializes the identical verified bytes into that runtime's supported file reference. A local Mac path alone does not prove a cloud runtime can read it. No helper server, generic subprocess, hidden HTTP or new credentials are supplied.

Uploads return `{id,raw}`. Metadata returns `{id,name,parents,size,mimeType,trashed,raw}` using explicit exact-ID fields. Raw download returns `{id,complete:true,bytesBase64,acquisition:{mode:"file-reference",reference},raw}`. `raw` retains the original response, while the adapter records the actual full byte length. Always request `download_raw_file:true, include_base64:false`, materialize the returned authenticated file reference, read bounded complete original bytes locally, and only then encode those local bytes for the packet. Provider inline base64, text excerpts, a declared `complete` flag alone, wrong parents/IDs/names/MIME, changed lengths and hash mismatches never establish closure. Credential-pattern checks run before storing response text and locally encoded bytes. This lexical guard is not a proof of arbitrary secret detection.

Each record upload receives exact metadata and raw readback before the next object. The immutable inventory then receives the same checks. Its v2 body retains generation, predecessor inventory reference, complete source-set hashes, capture interval, original source-clock bounds and the admitted-history boundary. Desired bytes close the pointer; exact prior bytes permit a bounded retry; newer or unrecognized bytes refuse. A later locally claimed generation blocks an old batch from issuing further calls. Pointer readback and inventory closure create no execution, publication or delivery receipt record.
