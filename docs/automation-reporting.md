# Private automation reporting

The reporting CLI reads validated immutable outcomes. Existing improvement-report producers and fleet responsibilities still own reporting and monitoring. This hub never reruns gameplay, quizzes, mail, Tasks or calendar actions. No remote service, OAuth, installation or account permission is needed for local operation.

```sh
mkdir -m 700 /absolute/private/reporting-store
npm run reporting -- --help
npm run reporting -- status --directory /absolute/private/reporting-store
npm run reporting -- import-improvement --directory /absolute/private/reporting-store --namespace maintenance --automation-id daily-maintenance --file /absolute/private/compact-report.json --dry-run
npm run reporting -- import-improvement --directory /absolute/private/reporting-store --namespace maintenance --automation-id daily-maintenance --file /absolute/private/compact-report.json
npm run reporting -- list --directory /absolute/private/reporting-store --limit 50 --query unresolved
npm run reporting -- serve --directory /absolute/private/reporting-store
```

Use an existing absolute canonical directory without symlink ancestry. `serve` prints its loopback URL and binds only `127.0.0.1`; stop its owned process with Ctrl-C. GET-only HTTP serves the same validated model. There are no rerun or cancellation controls.

## CLI contract

Each invocation prints one JSON result. Exit 0 means its local operation completed, 2 means invalid input or an operational refusal, and 3 means findings requiring attention. A completed review with partial evidence is a valid execution outcome; `coverage-partial` is evidence attention, not execution failure. Missing reports and delivery remain separate. Empty inventory means registered-only coverage with unknown undiscovered automations, never complete fleet coverage.

`status`, `diagnose` and `reconcile` return concise counters and bounded findings (20 by default), with `findingPage` totals and `--finding-cursor` continuation. `inspect` returns typed detail pages (50 per kind by default), totals and digest continuation cursors without a duplicate records array. Namespace/automation scope filters apply to all reads. These commands read the bounded store without writes or native actions. `validate` and `dry-run` validate a supplied record and ownership without writes. `publish-own-record` requires `--namespace` matching the envelope. `export-outcome --id <current-run-digest> --to <absolute-private-output>` writes a bounded sanitized outcome file without cloud calls. It refuses incomplete scans, invalid/conflicted/superseded runs, known credentials, private paths/account addresses in exported text, and unsafe artifact URLs. Identical output retries converge; different existing bytes remain unchanged. `get --id` retrieves an exact immutable digest, including historical revisions. `list` supports namespace, automation, bounded search, digest cursor and limit 1–200. Its cursor addresses observed immutable IDs; restart pagination to discover concurrent insertions before a cursor. CLI help lists exact flags. The existing `agent reporting --file <request.json>` exposes the same core JSON operations.

Scans inspect at most 200 root entries and 5,000 namespace entries, including pending files. Each record is bounded to 32 KiB. Exceeding a bound or finding corrupt/mismatched canonical bytes yields explicit incomplete coverage and suppresses accepted run execution. Pending write bytes are ignored within those bounds. A scan may precede a later write and is not a transactional filesystem snapshot. No all-account completeness claim follows.

## Version 1 record schema

Every envelope has exactly `schemaVersion`, `namespace`, `automationId`, `kind`, `key`, `revision`, `previous`, `recordedAt`, and `data`. Version is 1. Namespace and automation ID are safe identifiers of at most 120 characters. Keys retain bounded original logical identities, including compact-report run IDs; keys never form filesystem paths. Timestamps are canonical UTC. Revision zero has null predecessor. Later revisions reference the exact prior digest, same identity, preceding revision and nondecreasing record clock. Run occurrence identity and receipt subject stay fixed. Missing or invalid predecessors and divergent leaves remain visible and unusable.

`automation` data contains `name`, `enabled`, `schedule`, `environment`, `nativeRef`, `model`, `destination`, nullable `freshChat` and `archiveOnSuccess`, `sourceRef`, and `observedAt`. It preserves declared native configuration; it does not configure a scheduler. Freshness checks the original native observation, not just the latest envelope.

`occurrence` data contains `scheduledFor` and `expiresAt`. Expected slots exist independently of observed invocations. An expired slot without a validated run is overdue. Invalid or conflicted invocation evidence leaves the slot unknown. No slot or archive membership implies completion.

`run` data contains nullable `occurrenceKey`, `execution`, `coverage`, nullable `report`, and bounded `evidenceRefs`. Execution is unknown, running, blocked, pending-approval, completed, failed or skipped. Terminal execution cannot change state in a successor. A retry uses a new invocation key. Same-state successors can append corrected report/coverage evidence; old facts remain immutable. Coverage is complete, partial or unavailable. Optional `telemetry` contains measured `runtimeMs`, `inputTokens`, `outputTokens` (unavailable values are null), and `sourceRef`. Optional `timing` contains nullable `startedAt`, `lastHeartbeatAt`, `endedAt`, plus `observedAt` and `sourceRef`. Event times are ordered and no later than the source observation; observation is no later than the envelope. Omitted timing projects explicit nulls. Report generation, import and envelope clocks never become actual run events. Values are supplied measurements, never estimates of provider billing. The reader preserves raw measured values; it invents no trends from missing telemetry.

The report union also accepts generic `type: automation-outcome`, `schemaVersion: 1` for briefing, URECA, Krillion, Wooclap and future workflows. Exact fields are `schemaVersion`, `type`, `runId`, `provenance`, nullable manual `scheduledFor`, `status`, `coverage`, `availability` (available/unavailable), `summary` (at most 600 characters), `artifactLinks` (bounded safe HTTPS label/URL pairs), nullable original `sourceWindow`, and `generatedAt`. Available requires a compact outcome or artifact. Generic availability is preserved independently of execution. No review kind is invented for unrelated workflows.

The compact report is the existing [improvement-report](improvement-report.md) v1 contract. Its execution/coverage/run identity must match the envelope, and scheduled provenance must match the exact occurrence time. `import-improvement` uses deterministic slot identity and scheduled-time bytes for the occurrence, preserving the original report generation time on the run. Distinct attempts for one slot therefore share one expected occurrence. Manual reports create no expected slot. Publication retry is safe after interruption between the two immutable writes and never replays the underlying work.

`publication` and `delivery` data contain exact run digest `subject`, `state` (pending, accepted, verified or failed), and nullable `evidenceRef`. Verified requires an evidence reference and cannot regress in a successor. Subjects must be current valid nonconflicting runs in the same producer scope and precede the receipt. Acceptance is not verified publication; publication is not user delivery. Both remain attributable reported claims. Their references do not authenticate a provider or recipient.

`issue` data contains bounded searchable `title`, state open/acknowledged/resolved, and `evidenceRefs`. Resolution requires evidence. Immutable revisions retain acknowledgements and later reopenings. Only compact sanitized outcomes and safe artifact references belong in these records. Keep secrets, raw logs, full mail and sensitive account payloads out. Publication rejects recognized API-key, Bearer, private-key and credential-URL patterns. Cloud export explicitly selects compact outcome fields and hashed timing references; it excludes local evidence refs. Its additional policy refuses recognizable local paths, account email addresses, raw headers and credential-bearing URLs. Refusal leaves publication pending. These bounded lexical checks cannot establish that arbitrary prose contains no secret; producers still own sanitization.

## Storage and ownership

Each producer writes only `<store>/<namespace>/<sha256>.json`. The SHA-256 covers recursively sorted JSON. A fully written fresh pending file is hard-linked to the canonical digest, read back, then the owned pending file is removed. Identical retries converge; differing records are retained. Readers derive the view from all validated facts; producers never write a shared index or dashboard. Namespace selection is cooperative ownership, not OS-user authentication. Ordinary trusted private directories, collision-resistant hashes, atomic same-filesystem hard links and no hostile concurrent ancestor replacement are assumptions. No power-loss durability follows.

`pendingPublicationQueue` derives from runs without a verified publication receipt. Retrying that queue means retrying reporting only. Private sync/publication and the existing ChatGPT notification workflow remain parent-owned. No new notification channel is created. Keep a pending notice distinct from an independently verified user delivery.

## Emmy infrastructure and private Drive records

All reporting code, schemas, commands, verification and private fallback evidence live in Emmy. The verified private Drive `Reports/Records` subtree is the shared sanitized canonical read model. Each producer owns one namespace directory. Cloud producers upload the same version1 envelopes and digest filenames that the local core validates. Native producers keep original evidence under ignored `.local/`, then invoke the deterministic transport adapter into their own synced namespace. The independent CLI/dashboard reads that shared sanitized store; no producer writes a dashboard or index. Private folder IDs, account/path mapping and deployment configuration stay ignored.

```sh
npm run reporting:transport -- --source-directory /absolute/private/fallback --directory /absolute/verified/synced/Records --namespace producer --dry-run
npm run reporting:transport -- --source-directory /absolute/private/fallback --directory /absolute/verified/synced/Records --namespace producer
```

The adapter validates bounded full own-namespace history and every projected record before writing. It preserves keys, revisions, actual event/report/source clocks and status/coverage. It rebinds predecessor hashes to their exact sanitized predecessors. Every projected run retains a source-record digest, so differences excluded from a compact summary cannot collapse contradictory branches. Correlation conflicts remain visible as unknown execution in the reader. Original local references remain in the fallback; projected references are digest bindings. Safe generic artifact links remain links. Legacy manual reports have a nominal `scheduledFor` despite being manual; the explicit conversion sets generic scheduledFor null and reports that normalization while retaining the complete source record digest and actual clocks. No expected slot is invented.

Original publication/delivery receipts bind exact source bytes and are explicitly skipped. Create new target receipts only after readback of those target bytes. Local synced-directory publication remains pending remote verification. A cloud reader must independently verify exact folder, filename, canonical digest and returned bytes. Upload acceptance, sync, verified publication and user delivery stay separate. The CLI pages source-to-target mappings and manual normalizations in bounded groups of 50. Equivalent source/target paths refuse before writes. There is no automatic deletion or retention of immutable history; the documented scan bound remains a scaling limit.

Inventory native and cloud definitions before migrating adapters, including disabled definitions and missing fields. Preserve authority, timings, model, destination and lifecycle fields privately. Parent owns cloud prompt changes. Future prompts publish their own bounded outcome after work and preserve original workload success criteria. Expected slots come from the existing fleet/schedule owner, independently of whether a producer invokes. Reporting retries never replay effects. Missing or uncertain sync remains pending and must use the existing failure-notification workflow.

The source repository is public. Keep runtime records, raw logs, native IDs and personal state under ignored `.local/` or the verified private operational folder. Never push them to public source. Git metadata/push permissions do not prove private runtime access. No new private GitHub repository, visibility change, credentials or permissions are implied.

Exactly one dedicated native local upkeep automation maintains managed names, paths, safe links and freshness in the verified private reporting copy. It does not invent outcomes, edit artifact content or permanently delete anything. It requires verified local deployment and synced mapping. Preserve other schedules/models. Fresh-chat/archive fields and execution require separate native readbacks; unsupported controls stay unverified. Existing challenge files and original folders remain untouched.

## Managed repair and cloud preparation

`npm run reporting:upkeep -- plan --source-directory <fallback> --directory <verified-primary> --namespace <owner> --to <private-plan>` proposes exact byte-preserving repairs. `npm run reporting:upkeep -- apply --file <private-plan>` explicitly applies them. Default `reconcile` remains read-only. Plans bind canonical root/directory identities, exact sanitized fallback expectations, original names and byte hashes. Apply revalidates the complete plan before writes, refuses changed/conflicting targets, and uses exclusive full-byte links with guarded old-name removal. Identical retries converge after interruption. Original plans retain names so aliases can be recreated for a deliberate rollback. No artifact content changes, permanent deletion or overwrite of unknown bytes is authorized. File/namespace case aliases are retained; actual APFS tests cover sole-entry deletion and duplicate spellings. Unknown and pending files, stale/missing outcomes and unproven links remain findings. One cooperating writer and immutable source/candidate bytes are assumptions. Local moves/coalescing do not preserve or establish Drive file IDs or sync atomicity.

Synced namespaces must already exist and have verified mapping. Missing folders remain pending; transport and upkeep never provision them locally. The generic publisher's `--synced` guard requires an exact existing namespace and export-safe record. The installed primary-store launcher applies it automatically; ignored fallback publication can still initialize its own namespace. Provision future folders through exact Drive parent IDs, verify remote metadata and actual local arrival, then enable the writer. A local mkdir is not Drive identity proof.

Build a self-contained Node24+ standard-library preparation tool with `npm run build:reporting-cloud`. It mechanically bundles the actual product validators, writes an exact-source/hash manifest under ignored `.local/reporting-cloud/`, and copies the [version1 structural schema](../schemas/automation-reporting-v1.schema.json). The generated tool supports `prepare --namespace <own> --automation-id <id> --file <input> --to <absolute-output>` and `verify --namespace <own> --automation-id <id> --file <canonical> --id <digest>`. It computes bytes/hash without changing supplied values. Actual code enforces cross-field clocks/privacy; schema documents structure. Namespace ancestry needs a separate complete namespace read. An unavailable cloud Node runtime is a blocker; install nothing, use the existing authorized native bridge. Native source artifact readability does not prove execution in another environment.

Provider invocation IDs are used only when actually exposed by trusted context. Otherwise persist a generated opaque producer-invocation ID before upload, explicitly label its source, and keep provider ID unavailable. Never present it as a native/provider ID or replay work to recover it. The existing fleet/schedule owner independently publishes expected occurrences under its delegated authority; expected slots do not prove a trigger. If a native invocation starts before its expected slot, `execution: running` with `report: null` and actual sourced timing is valid. Scheduled generic reports cannot predate their slot; retain missing report rather than advancing clocks or changing the legacy review contract. Existing workload authority/time guards remain separate.

Empty inventory and enabled definitions with no observed invocation require attention and explicit unknown/observation-needed state, without inventing failed runs. Disabled definitions require no new run. Reported completion and partial coverage remain independent. Per-automation detail links its latest recorded evidence IDs; that selection is not proof of the latest native invocation.
