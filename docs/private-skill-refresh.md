# Revalidate the approved private skill capsule

Use `node scripts/private-skill-refresh.mjs <private-config.json> <fresh-cloud-capture.json> <new-attempt-directory>` from an explicitly installed reviewed version. The restricted runner imports only the inventory and release integrity helpers. It invokes no maintenance command, subprocess, network request, remote writer, or bundled skill tool.

The private version 1 configuration pins the reviewed runtime revision, inventory snapshot, complete local capsule path, installed source bindings, and accepted cloud consumer. `cloud` contains exact `fileId`, `parentId`, owner email, raw byte count, and SHA-256. `consumer` repeats the accepted file ID, hash, revision, and snapshot. The caller verifies the configuration and installed runner against its trusted deployment hashes before invocation.

Acquire current metadata for the exact folder and file through the connected Drive tool. Fetch the complete authenticated raw file. Save a private capture with `observedAt`, `rawPath`, `parent`, and `file`. These metadata objects use the connector's `id`, `mime_type`, `shared`, `permissions`, `parent_ids`, and `size` fields. `observedAt` is the original acquisition clock, never a reread clock. Captures older than 15 minutes or from the future refuse. The caller retains original connector receipts separately. Supplied captures remain reported evidence to the CLI, which cannot authenticate provider truth.

The runner checks exact owner-only permissions, the private parent, complete raw bytes and hash, accepted consumer binding, and all release file hashes. It materializes a fresh runtime, refreshes only the approved installed sources, and requires the selected inventory bytes and snapshot to remain identical. It rereads every selected entry, dependency, source notice, and the separately scoped root licences. Each attempt retains its request, runtime, source acquisition record, and terminal result in a new directory. Reusing a directory refuses.

Unchanged bytes produce `operation: unchanged` and `remoteWrite: false`. This is an idempotent revalidation of the existing accepted capsule. It never renews the snapshot's original observation clock or claims semantic guidance adoption or native registration. Source discovery changes, missing files, content or version drift, new or changed licences, dependencies, and uncertain cloud reads hold the attempt. Accepted local capsule and cloud selections remain untouched. Candidate changes inside the attempt are unaccepted diagnostic evidence.

For a separately reviewed source release, run `prepare-candidate <private-config.json> <fresh-cloud-capture.json> <approved-candidate.json> <new-attempt-directory>`. The candidate pins `path`, `sha256`, `bytes`, `revision`, `snapshot`, and the original independent `approvalRef`. This reference is supplied evidence, not authenticated approval. The caller must inspect the actual verdict before acting. The command verifies the last-good cloud capsule and both source inventories. It then retains one immutable `upload-request.json`. Unchanged candidates have no upload request.

The caller performs the returned upload once through the supported Drive connector. It creates a new private file and never updates the accepted file. Before uploading, discover the exact deterministic candidate name and resolve any previous pending attempt. Retain the original tool receipt. On an uncertain response, keep the request pending and rediscover by exact returned ID or the unique full-hash name. Never retry blindly or create a replacement to resolve uncertainty.

After complete exact-ID metadata and raw download, run `verify-candidate <attempt-directory> <upload-receipt.json> <fresh-candidate-capture.json>`. The receipt binds `fileId` and the returned `requestSha256`. This checks the candidate's private parent, permissions, size, complete raw hash, and release integrity. The terminal state is `candidate-verified`, with `selectionChanged: false` and `activation: held-consumer-acceptance`. Repeating preparation in that directory refuses, so an interrupted upload cannot silently issue a second request there.

There is no automatic accepted-consumer selection transition. A verified immutable candidate is private transport evidence. It is not accepted consumer selection. The existing consumer uses exact out-of-band ID and hash pins; it has no established mutable selection route. Establish that acceptance before replacing any binding or enabling a job whose scope requires actual changed-capsule refresh. The accepted file and consumer remain intact throughout candidate failure or uncertainty. Do not describe candidate transport or unchanged revalidation as a completed automatic refresh.

Run `node --test test/private-skill-refresh.test.mjs test/skill-inventory.test.mjs`, an actual fresh capture through the CLI, and `npm run check`. Tests cover idempotence, source failures, cloud identity, sharing, raw corruption, freshness, consumer pins, and preservation of accepted selections. These checks add no finite or TLA+ theorem. Native schedule timezone, first occurrence, settings, execution, and future consumer adoption require separate readbacks.
