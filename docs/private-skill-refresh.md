# Revalidate the approved private skill capsule

Use `node scripts/private-skill-refresh.mjs <private-config.json> <fresh-cloud-capture.json> <new-attempt-directory>` from an explicitly installed reviewed version. The restricted runner imports only the inventory and release integrity helpers. It invokes no maintenance command, subprocess, network request, remote writer, or bundled skill tool.

The private version 1 configuration pins the reviewed runtime revision, inventory snapshot, complete local capsule path, installed source bindings, and accepted cloud consumer. `cloud` contains exact `fileId`, `parentId`, owner email, raw byte count, and SHA-256. `consumer` repeats the accepted file ID, hash, revision, and snapshot. The caller verifies the configuration and installed runner against its trusted deployment hashes before invocation.

Acquire current metadata for the exact folder and file through the connected Drive tool. Fetch the complete authenticated raw file. Save a private capture with `observedAt`, `rawPath`, `parent`, and `file`. These metadata objects use the connector's `id`, `mime_type`, `shared`, `permissions`, `parent_ids`, and `size` fields. `observedAt` is the original acquisition clock, never a reread clock. Captures older than 15 minutes or from the future refuse. The caller retains original connector receipts separately. Supplied captures remain reported evidence to the CLI, which cannot authenticate provider truth.

The runner checks exact owner-only permissions, the private parent, complete raw bytes and hash, accepted consumer binding, and all release file hashes. It materializes a fresh runtime, refreshes only the approved installed sources, and requires the selected inventory bytes and snapshot to remain identical. It rereads every selected entry, dependency, source notice, and the separately scoped root licences. Each attempt retains its request, runtime, source acquisition record, and terminal result in a new directory. Reusing a directory refuses.

Unchanged bytes produce `operation: unchanged` and `remoteWrite: false`. This is an idempotent revalidation of the existing accepted capsule. It never renews the snapshot's original observation clock or claims semantic guidance adoption or native registration. Source discovery changes, missing files, content or version drift, new or changed licences, dependencies, and uncertain cloud reads hold the attempt. Accepted local capsule and cloud selections remain untouched. Candidate changes inside the attempt are unaccepted diagnostic evidence.

For a separately reviewed source release, run `prepare-candidate <private-config.json> <fresh-cloud-capture.json> <approved-candidate.json> <new-attempt-directory>`. The candidate pins `path`, `sha256`, `bytes`, `revision`, `snapshot`, the original independent `approvalRef`, and optional explicitly reviewed replacement `bindings`. This reference is supplied evidence, not authenticated approval. The caller must inspect the actual verdict before acting. The command verifies the last-good cloud capsule and its retained inventory offline, then refreshes the candidate against its own exact reviewed installed bindings. This permits a reviewed source-version migration after the old installation disappears, without fabricating that installation or weakening ordinary unchanged checks. It retains one immutable `upload-request.json`. Unchanged candidates have no upload request.

The caller performs the returned upload once through the supported Drive connector. It creates a new private file and never updates the accepted file. Before uploading, discover the exact deterministic candidate name and resolve any previous pending attempt. Retain the original tool receipt. On an uncertain response, keep the request pending and rediscover by exact returned ID or the unique full-hash name. Never retry blindly or create a replacement to resolve uncertainty.

After complete exact-ID metadata and raw download, run `verify-candidate <attempt-directory> <upload-receipt.json> <fresh-candidate-capture.json>`. The receipt binds `fileId` and the returned `requestSha256`. This checks the candidate's private parent, permissions, size, complete raw hash, and release integrity. The terminal state is `candidate-verified`, with `selectionChanged: false` and `activation: held-consumer-acceptance`. Repeating preparation in that directory refuses, so an interrupted upload cannot silently issue a second request there.

## Select a verified private candidate

The private selection configuration pins one mutable selector ID, its current complete raw hash, byte count and generation, one immutable history file with the same selection bytes, the accepted capsule binding, owner, parent, installed source bindings and private local state home. The initial selector and immutable generation-zero history both reference the previously accepted exact capsule. Verify both through the connector before saving the initial `current.json` under that home. This creates no native runtime registration or entitlement.

Run `prepare-selection <current.json> <fresh-captures.json> <verified-candidate-attempt> <new-selection-attempt>`. The capture object contains `selector`, `history`, and `candidate` raw captures. The command acquires a persistent home-wide `writer.lock`, verifies the local predecessor and complete old selector/history, verifies the candidate and both approved source inventories, and retains `pending-selection.json` plus new `selection.json`. It returns one immutable history upload. The new selection records the previous binding and immutable history ID.

Upload that history once through Drive, retain the exact receipt, and obtain complete exact-ID private readback. Run `prepare-selector-update <selection-attempt> <history-receipt.json> <fresh-history-capture.json>`. The receipt contains the returned `fileId`. Only verified new history produces an exact-ID `update_file` request for the existing selector. Immediately reacquire the unchanged old selector before issuing that update once. Never update a capsule or history file. No conditional-write primitive is exposed by this connector. The persistent lock serializes cooperating updater invocations; unrelated external writers and hostile filesystem mutation remain outside this contract.

After the selector write, reacquire selector, new history and selected capsule by their exact IDs. Run `complete-selection <selection-attempt> <fresh-captures.json>`. The command requires every full raw hash, private metadata, exact selected binding and complete runtime inventory. It consumes all selected guidance and notices locally from the actual cloud readback, then atomically replaces local `current.json`. It retains the old binding and every immutable remote capsule/history. Successful repeated completion converges without another remote write. A diagnostic failure after local selection can be resolved by the same exact readbacks.

An uncertain upload or selector response keeps the writer claim and pending request. Do not retry the write or release the claim automatically. Exact-ID readback may resolve an already completed selector update. A missing, old, conflicting or unavailable selector cannot advance local selection. The old capsule and immutable selection history remain available even when the mutable selector's outcome is unknown. Inspect pending requests and attributable remote state before any manual recovery. This protocol does not claim power-loss durability or atomicity across Drive and the local filesystem.

Run `check-selection <current.json> <fresh-captures.json> <new-attempt>` for daily idempotent revalidation of the accepted selector, history, capsule and installed approved sources. Unchanged bytes require no upload. Only a separately reviewed exact candidate may use the update protocol. Changed source content, identity, version, dependency or licence never approves itself. Native cloud-task adoption of the new selector route remains separate from exact remote selection readback and local consumer acceptance.

## Reach an explicitly reviewed source migration

Scheduled callers use `prepare-run <current.json> <fresh-captures.json> <reviewed-staged.json|-> <new-attempt>` before any strict installed-source check. A staged migration has `schemaVersion: 1`, the complete exact `expectedBinding`, and the independently reviewed `candidate` object described above. The saved caller pins the staged file's hash and verifies its original independent verdict. A nonempty `approvalRef` is supplied evidence, not proof of authorship or authority.

When the entire current binding matches the reviewed predecessor, the entry checks pending writer refusal and fresh exact selector/history/capsule bytes first. It then prepares the candidate using the predecessor's immutable capsule and retained inventory offline. Only the candidate's reviewed replacement source bindings are acquired. This branch can reach `awaiting-upload` even when the accepted old installed directory has vanished. It emits no network write and does not change accepted local or cloud selection. Continue with the existing exact-ID candidate/history/selector protocol only in the authorized scheduled run.

With `-` instead of a staged file, ordinary strict `check-selection` still applies and missing installed sources hold. If the exact reviewed candidate has already been selected with the reviewed bindings, the entry also uses unchanged validation. A conflicting predecessor, malformed plan, stale/corrupt remote capture or pending writer holds. Never fall back from a rejected staged migration to automatic version discovery. Retain original held runs; local staging does not establish successful future recurrence.

Run `node --test test/private-skill-refresh.test.mjs test/skill-inventory.test.mjs`, an actual fresh capture through the CLI, and `npm run check`. Tests cover idempotence, source failures, cloud identity, sharing, raw corruption, freshness, consumer pins, and preservation of accepted selections. These checks add no finite or TLA+ theorem. Native schedule timezone, first occurrence, settings, execution, and future consumer adoption require separate readbacks.
