# Run the daily improvement review

Use one improvement responsibility and the existing private journal. Daily maintenance finds new failures, checks unresolved ones, and makes justified small local repairs. A separate daily pass suggests opportunities. A twice-weekly [token review](token-review.md) examines cost per verified successful task. None needs to invent a change. The [incident audit](research/self-improvement-audit.md) records the initial gaps and distinguishes them from repaired incidents.

## Acquire the previous day's evidence

1. Recover the trusted installed runner, its selected private home, and the existing improvement responsibility. Read `AGENTS.md`, the installed pstack `poteto-mode` skill, the architecture, and relevant project verification instructions. Record the actual paths and versions privately. Pass these requirements to every worker and reviewer.
2. Establish the previous calendar day in `Asia/Singapore`, using a half-open interval. Retain the previous successful review cutoff too. Cover any unreviewed gap after a missed run without declaring an incomplete day clean.
3. Read authorized conversation deltas, operation receipts, current repository changes, unresolved findings, and owner corrections. Use supported native thread reads or parent-provided captures. Do not scrape denied session paths, read native databases, or extract credentials. Record missing sources, original content times, acquisition times, and page coverage.
4. Compare each candidate incident with retained repair and deployment evidence. Keep stable finding and effect IDs. A stale summary cannot reopen a verified repair. A new contrary observation can establish a new regression, with its own evidence.
5. State actual harm separately from potential impact. Keep unknown actors and causes unknown. An enabled schedule, accepted dispatch, completed worker, local test, installed runner, and live outcome are different evidence.

## Choose the smallest justified action

Use the [model policy](../AGENTS.md#standing-thread-and-model-policy). Select a model capable of the task before dispatch; a cheap failed attempt is not a saving. A daily lead owns classification and final review. Spawn helpers only when the expected work justifies the extra context and review. Do not create a second permanent implementation automation.

A small repair has a reproduced defect, understood cause, bounded local files, no unresolved ownership conflict, a reversible patch, and a decisive test. Inspect the working tree first and preserve user changes. Reproduce, change, run the targeted regression and required project checks, review the actual diff, and retain rollback instructions. Do not mix an unrelated repair into the same patch. Follow native project dispatch for a distinct coding objective.

Luna Max may implement a fully specified mechanical change with supplied inputs and acceptance criteria. Investigation, interpreting failed verification, schema changes, concurrency, source identity, or cross-system behavior are not mechanical work. Start those on an appropriate stronger model. Escalate at the first unexpected failure or expansion of scope; retain the failed evidence. Do not repeat the same failed premise with another patch.

For a substantial change, prepare a proposal containing the affected resources and users, current observed harm, plausible new harm, compatibility requirements, verification, deployment steps, and exact rollback. Continue independent safe work. Implementation or release outside the existing authority waits for the required decision. This review does not authorize privilege expansion, credential changes, deletion, paid services, unsolicited communications, deployment, or broad rewrites.

Calendar policy bindings and fleet replay changes from the initial audit need separate reviewed objectives. Never relabel those open gaps as fixed because this procedure was added.

## Retain a report the briefing can use

Write one derived JSON report under the selected private home's improvement directory, with a unique run ID. It references existing journal records and retained receipts; it is not a second authoritative incident registry. Keep old reports immutable. Do not use a mutable `latest` file as proof of freshness. The responsibility backup does not include this derived directory; preserve wanted report files separately while keeping canonical evidence in the journal.

The minimum report has these fields:

| Field | Required content |
| --- | --- |
| `schemaVersion`, `runId`, `day`, `timeZone`, `generatedAt` | Version 1, unique run identity, review day, `Asia/Singapore`, and actual generation time. |
| `reviewWindow`, `previousReviewRef` | Exact covered interval and prior accepted report or an explicit gap. |
| `inputRecordRefs`, `coverageGaps` | Existing journal/evidence references and missing or partial sources. |
| `requestedModel`, `resolvedModel`, `modelReadback` | Family and effort requested, concrete supported ID chosen, and observed settings or explicitly unavailable. |
| `items` | Stable finding ID, exact scope, original source time, acquisition time, evidence references, observed harm, potential impact, and cause status. |
| `items[].acceptance` | Separate `source`, `published`, `installed`, `guidance-loaded`, `adopted`, and `live-outcome` rows where applicable. Each has passed, failed, pending, unknown, or not-applicable status and its evidence/time. |
| `items[].change` | Local patch or commit, tests with actual results, independent review where required, affected resources, and rollback; null if unchanged. |
| `items[].nextAction`, `items[].briefingChangeKey` | Stable action and material-change identity. Preserve identical action text for unchanged fleet episodes. |
| `suggestions` | Separate proposed opportunities with benefit, evidence, overlap, effort, recurring cost, risk, and an acceptance check. |

Before the briefing uses a report, verify its review window, source ages, evidence references, and coverage. Preserve old source times; a newly written report is not a fresh provider read. Missing, stale, unfinished, future-dated, or inaccessible reports yield an explicit coverage limit. They must not yield “no issues found.”

Project material findings into the existing [briefing input](briefing.md), using separate exact `scope.effect` values for source repair, installation, and live acceptance. For example, “source fix passes regression” must not close “verify the next scheduled occurrence.” Use the original evidence references and correction authority, not the briefing itself. The existing checker decides whether declared support is current and complete. It does not parse this report automatically or authenticate its contents.

The morning owner adds a concise improvement section to the existing 07:15 Singapore briefing: verified changes, the remaining user-visible issue, and any real decision needed. Do not send a second competing daily digest. Suppress unchanged previously delivered details while retaining unresolved items privately. A report is delivered only after the normal same-message readback. If the local artifact is unavailable to the cloud briefing, use the existing authorized parent handoff and record that coverage gap until its readback succeeds. Never wait for a running review or delay the briefing to obtain a report.

## Review token efficiency twice weekly

Review the work since the previous accepted token review, including any gap. Use supported usage exports or explicitly supplied captures. Compare total planner, worker, reviewer, retry, and tool cost against verified outcomes. Keep measurements, estimates with methods, and unavailable data separate. A cheap failed attempt can increase total cost. Missing usage is not zero, and account-wide limits do not attribute usage to a task.

Inspect instruction duplication and length, stale or contradictory context, demonstrated truncation, repeated reads or tool calls, model fit, and coordination overhead. Repeated reads may be necessary after changed bytes or in an independent review. A character count is not a measured token count; a long conversation alone does not prove context overflow. Keep observations distinct from the cause of a failed outcome.

Use `token-review` for deterministic accounting of supplied captures, then interpret its explicit limits. Model downgrades need representative task-specific evidence under unchanged acceptance criteria. Suggest an upgrade when observed failures show inadequate capability. Never remove essential safety rules, owner constraints, evidence, or recovery instructions to improve a metric. No edits to private runtime prompts, hidden context mechanisms, global settings, or another project's instructions. A small local shortening needs semantic comparison, regression cases, required checks, and rollback. Substantial changes remain proposals.

Keep the review compact. Reuse the same report and journal references. Retain a measured/recommended summary, its coverage limits, and only material opportunities for the existing briefing. Do not create a growing parallel review registry or run live mail/calendar experiments.

Preserve the exact action, target, platform reason, whether execution is known absent or uncertain, and the relevant owner authorization. An opaque pending state is not enough to diagnose a setting.

Assemble the complete reviewable prompt before one supported update of the existing automation. Use read operations for status. Do not edit scheduler files directly or recreate a schedule to repair unknown metadata.

Scheduled tasks normally use a noninteractive approval policy when allowed. Work outside their permitted scope can fail rather than prompt. Keep the host available and the desktop app running for local tasks. These are prerequisites, not a diagnosis of a particular missed run. [OpenAI's scheduled-task documentation](https://learn.chatgpt.com/docs/automations) describes the supported behavior.

Do not change global or project security settings under the improvement grant. Recommend only the smallest identified setting with consequences after inspecting the actual blocked operation. Measure avoidable repeats and owner wait by category, not total prompts alone. Keep a manual rescue separate from the expected scheduled occurrence. Null next-run metadata alone proves neither failure nor recovery.
