# Run and accept an Emmy agent task

Use the [agent-task skill](../.agents/skills/agent-task/SKILL.md) and its [six-section prompt](../.agents/skills/agent-task/assets/task-prompt.md). This is a human task contract over existing tools. It adds no runtime or formal property. Keep standing context in the destination project, original private receipts under ignored `.local/`, and one accountable owner per change.

## Route and supervise

1. Classify the objective before choosing a chat. Create a fresh project-bound native task for a distinct objective. Continue a known chat only for the same objective when its context is needed. Shared repository or topic is insufficient. Independently started work may be observed, but discovery grants no instruction, continuation, or cancellation authority.
2. Discover the saved project and host through supported native tools. Use [disposable discovery](../.agents/skills/verify/features/routing.md#disposable-studio-task-discovery) to organize captures if useful. Preserve partial, stale, missing, and unknown membership explicitly. The index is an observation projection, never action authority or absence proof.
3. If private bindings select an authorized persistent dispatcher, recover the selection and exact objective through the trusted installed `dispatch` command. Follow [private dispatch recovery](native-dispatch.md), including its existing responsibility/import records. Keep that dispatcher pinned. Its fresh children own implementation. Otherwise use the authorized native route directly. A CLI proposal cannot grant authority.
4. Finalize the six-section contract and upfront acceptance criteria. Resolve actual installed skill paths and destination-supported model IDs immediately before dispatch. Follow the standing family, effort, and speed policy. Retain requested policy, resolved configuration, recorded settings, and observed execution separately. Report unavailable controls or readbacks.
5. Before `create_thread`, retain the exact creation intent, objective marker, request, destination, and attempt identity under ignored `.local/`. Use existing objective records where configured. Call the designated host's supported native `create_thread` with the discovered saved project ID and `target.environment.type = "local"`. Follow the [native host route](change-delivery.md#create-through-the-native-host-service). Durable cloud tasks do not establish native creation.
6. Preserve the response before another action. Resolve pending client IDs through native discovery before ready-ID reads. For an uncertain call or result, rediscover the exact objective, attempt, and any known native identity before retrying. Partial or missing search results cannot settle uncertainty. Never create a replacement to repair uncertain identity or membership. Apply the same caution to other uncertain native changes. Inspect the same saved object before repeating the action, and continue unrelated safe work.
7. Read back the returned task's actual host and saved project membership separately from the requested ID and working directory. If association is missing, use the supported operation on that same native ID within authority, then read it back. Preserve contrary observations. Read recorded settings separately. Missing evidence stays unverified.
8. The parent owns supported `read_thread` or bounded `wait_threads` monitoring using the actual host, ready ID, and current cursor. Carry cursors forward and back off unchanged state. Do not depend on child callbacks or wakeups. For a stall, inspect the exact blocker, current work, and relevant logs. Take a bounded action within authority or ask the owner a scope question. Do not expand into unrelated work.

Use plain progress descriptions: planned; attempted, pending, or uncertain; native identity known; running; evidence review; accepted or gaps. These words describe observations. They are not a new implemented state machine or an at-most-once guarantee.

## Review the handoff

The supervising parent reviews the actual changed artifact and original receipts, not only the child's summary. Retain:

- Exact source and resulting revision, plus dirty state and changed artifacts.
- Each acceptance criterion mapped to original receipt locations, actual outcomes, failures, and gaps.
- Evidence labeled observed or reported, with scope exercised and material freshness or coverage limits.
- Unfinished work, uncertain effects, and the next owner and action.

Partial evidence cannot support complete acceptance. A child completion message, title, or passing test does not prove deployment, delivery, effective access, or external adoption. Missing telemetry need not stop unrelated bounded work. Disclose which conclusions remain unsupported.

Separate handoff acceptance from operational deployment. A reviewed local change can be accepted for its declared scope while installation or adoption remains unverified. Reuse the existing project verification and release gates for those later actions.

The [manual acceptance recipe](../.agents/skills/verify/SKILL.md#agent-task-workflow-acceptance) checks this procedure without external writes.
